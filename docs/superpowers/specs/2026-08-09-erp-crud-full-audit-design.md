# ERP 全页面 CRUD 接口巡检与修复设计

## 目标

对当前 ERP 的全部页面及其可触发写操作做端到端巡检，修复新增、编辑、删除、启停用、提交、审核、结算等操作中的接口错误或失败，并用自动化回归测试防止问题复发。

## 范围

- 覆盖 `frontend/src/router/index.ts` 注册的全部业务页面，并同时检查未直接注册但被页面复用的视图与组件。
- 覆盖页面可触发的全部写操作，包括新增、编辑、删除、启停用、提交、审核、驳回、关闭、结算、核销、报工、入库、出库等业务动作。
- 只读页面需验证它们没有伪装成可写操作的失效按钮或错误请求，但不为它们强行增加 CRUD 能力。
- 没有删除业务设计的单据不新增删除接口，继续遵守既有状态流转和审计规则。
- 备份恢复只验证接口契约、文件校验、确认词和权限控制，不执行真实数据库恢复。

## 数据安全

- 页面实测可以连接本机 ERP 数据库。
- 实测创建的数据统一使用 `CODEX-CRUD-` 前缀或能够明确追踪到该前缀的关联字段。
- 只修改或删除本轮创建的临时记录，不修改或删除任何已有业务数据。
- 对无法安全删除的审计型单据，保留临时记录并在巡检报告中明确列出，不绕过业务约束清理数据。

## 巡检架构

采用三层互补方式：

1. 建立页面、前端 API、FastAPI 路由、请求 Schema、Service 和 Model 之间的映射，静态核对路径、HTTP 方法、参数名、类型和统一响应结构。
2. 通过后端 API 测试验证成功与失败分支、事务结果、权限和状态流转。
3. 通过本地页面实测验证表单数据、按钮状态、错误提示、成功提示和列表刷新。

每个写操作按以下链路追踪：

```text
页面表单或按钮
  -> 前端 API 参数
  -> FastAPI 路由与请求 Schema
  -> Service 事务和业务校验
  -> 数据库结果
  -> 统一响应解析
  -> 页面刷新与用户提示
```

## 修复原则

- 先复现并记录故障，再补充能够失败的回归测试，最后做最小范围修复。
- 修复目标包括：路径或 HTTP 方法不一致、字段名或字段类型错误、必填项缺失、响应结构解析错误、事务失败、权限误判、错误未展示，以及成功后列表未刷新。
- 保留工作区现有未提交改动，不覆盖、不回退、不重写无关文件。
- 遵循项目现有 FastAPI、SQLAlchemy、Pydantic、Vue 3、Axios 和 Element Plus 模式，不做与 CRUD 故障无关的架构重构。
- 若底层 API 或 Schema 必须调整，同步更新所有前端调用、测试和相关业务依赖。

## 错误处理

- 合法请求返回项目统一成功响应，并让页面显示成功提示和最新数据。
- 重复编码、缺少必填项、非法引用、权限不足、非法状态流转和并发冲突返回明确的业务错误，不泄漏内部异常。
- 前端优先展示后端统一响应中的业务消息；网络错误或非标准响应使用明确的页面级兜底提示。
- 写操作期间防止重复提交；无论成功或失败都正确恢复加载状态。
- 事务中的任何步骤失败时回滚，不留下部分写入结果。

## 测试与验收

每个实际可写页面至少验证一个合法写操作；对具有编辑、删除或状态流转能力的页面分别验证对应操作。重要失败分支至少覆盖重复值、缺少必填项、非法状态流转或无权限中的适用场景。

验收分为五层：

1. 新增的定向回归测试能够复现原故障，并在修复后通过。
2. 后端完整 `pytest` 测试通过。
3. 前端完整 Vitest 测试通过。
4. 前端 TypeScript 类型检查与生产构建通过。
5. 本地页面逐页实测通过，浏览器中无相关未处理错误。

最终交付巡检报告，按页面列出：页面用途、写操作、对应接口、验证结果、修复内容、只读原因，以及受业务状态或权限限制的操作。

## 非目标

- 不重新设计页面视觉样式。
- 不新增现有产品范围之外的 CRUD 功能。
- 不执行真实备份恢复。
- 不清理、覆盖或提交与本轮修复无关的现有工作区改动。
